# ChampionCreator

ChampionCreator は、Pokemon Champions / Pokemon Showdown 系のダメージ計算に準拠しながら、複数の仮想敵条件を同時に満たす能力ポイント配分を探索する静的 Web アプリです。
耐久調整、火力ライン、素早さラインを同じ作業画面で扱い、条件を満たす候補の SP 配分、使用SP、残りSP、最厳条件、ダメージ詳細を比較できます。

公開URL: <https://championcreator.suisui-swimmy.com/>

使い方ガイド: <https://championcreator.suisui-swimmy.com/guide/>

プライバシーとデータの取り扱い: <https://championcreator.suisui-swimmy.com/privacy/>

画面の操作手順は使い方ガイド、計算・保存・同期の詳細仕様と対応範囲はこのREADMEを参照してください。

## 概要・主要機能

- 複数の仮想敵・複数攻撃を含む耐久条件を同時に満たす `H / B / D` 配分の探索
- 調整対象が相手を倒す `A / C` 火力ライン、相手や任意実数値に対する `S` ラインの算出とSP予算への統合
- 直接攻撃と、明示した定数ダメージ・回復の順序付き評価
- 全合格候補の比較・並び替え・適用、最厳条件とダメージ内訳の表示
- `残りSPで耐久最大化`による、耐久指数を基準にした別の配分比較
- 日本語・フォーム名の解決、使用率に基づく入力候補と初期入力
- 調整対象・仮想敵ボックス、ブラウザ下書き、JSONバックアップ、URL共有
- 任意のGoogleログインによるボックス同期・ブラウザ別クラウド下書き

操作手順と計算例は[使い方ガイド](https://championcreator.suisui-swimmy.com/guide/#calculation-example)を参照してください。この文書では、入力が計算・表示・保存へどう反映されるかと、その対応範囲を扱います。

## システム構成と責務

React 19 / TypeScript / Viteを使う静的Webアプリです。計算と通常編集はブラウザ内で実行し、Googleログイン後に初回統合を完了した場合だけFirebaseの同期経路を利用します。テストはVitest、配信はGitHub Pagesを前提とします。

| 境界 | 主な責務・実装 |
| --- | --- |
| 入力・画面 | [App.tsx](src/App.tsx)、[UI変換](src/ui/defenceSearchUi.ts): 入力文字列、編集状態、シナリオ種別を管理し、計算用の条件を組み立てる |
| 名前の解決 | [resolver](src/localization/resolver.ts): 種別ごとに日本語・別名をShowdown canonical nameへ解決する |
| domain | [model.ts](src/domain/model.ts)、[championsStats.ts](src/domain/championsStats.ts): Build、Scenario、SP制約、評価結果を表現する |
| 直接攻撃 | [smogonAdapter.ts](src/calc/smogonAdapter.ts): domainをCalcの`Pokemon` / `Move` / `Field` / `Side`へ変換する |
| HPの推移 | [hpEventRules.ts](src/calc/hpEventRules.ts)、[simulateHpSequence.ts](src/calc/simulateHpSequence.ts): 明示したHPイベントと直接ダメージを順に評価する |
| 探索 | [src/search/](src/search/): 耐久配分、火力・素早さライン、耐久指数による配分を評価する |
| 非同期実行 | [Worker](src/worker/defenceSearchWorker.ts)、[client](src/worker/defenceSearchWorkerClient.ts): 耐久探索と耐久最大化の進捗・中断・結果を受け渡す |
| 保存・共有 | [shareState.ts](src/ui/shareState.ts)、[boxStorage.ts](src/ui/boxStorage.ts)、[enemyBoxStorage.ts](src/ui/enemyBoxStorage.ts)、[src/share/](src/share/): 入力条件を版付きデータへ変換・復元する |
| 任意の同期 | [src/sync/](src/sync/): 認証、UID別保存、未送信変更、競合、クラウド下書きを扱う |
| データ生成・配信 | [scripts/](scripts/)、[Pages workflow](.github/workflows/deploy-pages.yml): catalog・使用率データの生成、validation、静的HTMLと配信artifactを作る |

UIの入力文字列はresolverを通り、`exact` / `alias`だけがdomainの`EntityRef`になります。入力不足、`ambiguous` / `not-found`、計算未対応を無関係な既定のポケモン・効果へ置き換えず、計算開始時のエラーや待機表示として扱います。解決済みcanonicalからCalc入力へ変換し、その計算結果を検索・表示へ渡します。画像、日本語表示名、使用率順位は直接ダメージの計算条件ではありません。

## 入力モデル・SPモデル

| モデル | 入力・役割 |
| --- | --- |
| `Build` | ポケモン・フォーム、レベル、性格、個体値、SP、特性、持ち物、テラスタイプ、通常タイプ上書き、ダイマックス、状態異常 |
| `ScenarioFormState` | 有効／無効、`耐久調整` / `火力調整` / `素早さ調整`、順序を持つ攻撃カード。調整種別ごとに専用の計算入力へ変換する |
| `Scenario` / `ScenarioHit` | 耐久探索の仮想敵条件と攻撃順。各攻撃は相手のBuild、技、回数、ランク、急所、場・両側条件、HPイベントを持つ |
| `SurvivalConstraint` | 必要耐久回数と必要生存率。攻撃カードごとの到達点で評価する |
| `ScenarioEvaluation` / `CandidateResult` | ダメージロール、HPイベント、生存率、合否、SP配分、残りSP、最厳条件。保存する入力条件とは別の計算結果 |

実際の画面は白紙から開始し、下書きがある場合も明示的な復元を待ちます。画面用の既定値と、旧保存形式やURL共有の復元に使う既定値は同一とは限りません。保存と共有の互換性はそれぞれの節を参照してください。

Pokemon Champions の Stat Points / SP を探索単位にしています。

- 各能力は `0..32 SP`
- 6能力合計は `66 SP` まで
- 画面から作成する条件の個体値は全能力31固定で、個体値を変更する入力欄はありません
- `0 SP` は `0 EV` として扱います
- `1 SP` 以上は `4 + (SP - 1) * 8 EV` へ変換します
- `32 SP` は `252 EV` です
- `@smogon/calc` へ渡す直前に、実数値が一致する Showdown EV 相当へ変換します

レベルは調整対象・各攻撃カードとも50が既定値です。ロック解除時だけ1〜100を入力でき、再ロックで50へ戻ります。個体値を持つdomainと、個体値31固定の画面入力は区別します。

## 計算・探索仕様

<a id="damage-calculation-boundary"></a>

### 直接ダメージ計算の責任範囲

直接攻撃のダメージロール、タイプ相性、タイプ一致補正、ランク、補正順、丸めは`@smogon/calc`を基盤とします。計算世代は`Generations.get(9)`です。アプリ独自のダメージ式・タイプ相性・乱数分布で最終結果を決めたり、Calcから返ったdamage配列へ倍率を後付けしたりしません。

計算経路は、固定upstreamのnative対応、戦闘中の効果が完全に同じと確認した限定的なexact alias、再現可能なCC compatibility patchに分かれます。metadataが入力候補へ存在することと、そのmechanicsを計算できることは別です。似た効果への代用や、未対応効果を無効果として通すことは計算対応に含めません。

現在の依存は`@smogon/calc@0.11.0`のupstream `e7fd7e59f3eef7ea42fba3c8b83261cb4a14109d`（監査日2026-09-11）をbaseとする[`smogon-calc-0.11.0-e7fd7e5-cc-champions-moves-v1.tgz`](vendor/smogon-calc-0.11.0-e7fd7e5-cc-champions-moves-v1.tgz)です。patchの適用順、出典、artifactのSHA-256 / integrity、native化時の撤去条件は[`smogon-calc-compat.json`](vendor/smogon-calc-compat.json)、採用判断は[監査記録](vendor/smogon-calc-audit-2026-09-11.md)にあります。Gen9の特性無視判定・通常タイプ上書き・次の4技を補完し、native対応とpatchを二重適用しません。

<a id="championsの技データ補完"></a>

#### 技データ・特性の対応

固定upstreamのChampions用`CHAMPIONS_PATCH`と同じ値を、CCが使うGen9データへ投影します。[4技のpatch記録](vendor/smogon-calc-champions-moves-v1.md)から固定SHAの出典へ辿れます。計算世代全体をChampionsへ切り替えているわけではありません。

| 技 | CCで使うデータ |
| --- | --- |
| ねらいうち | 威力85 |
| スターアサルト | 威力170 |
| きりさく | 威力80 |
| でんこうそうげき | 威力120、パンチ技 |

威力欄と耐久・火力の計算は同じCalcデータを使います。既存の任意威力に対応する技の設定には影響しません。でんこうそうげきのパンチ判定は、てつのこぶし・パンチグローブなどの既存Calc処理と、接触反動の判定にも反映します。

- `はどうのぼうご`は、接触技の最終ダメージを半減し、`えんかく`または`パンチグローブ`で非接触扱いになった技には適用しません。接触半減・`かがくへんかガス`・`とくせいガード`はnative経路で評価し、Gen9で不足する`かたやぶり`系と特性を無視する技の対象リストだけを補完します。補完は参照済みPokemon Showdown実装に合わせた暫定対応で、実機仕様または同等のGen9 native対応時に再監査します
- `ふとうのけん`・`ふくつのたて`は、既存の保存条件との互換性のため発動済みとしてCalcへ渡します。入力ランクに対するA／Bの1段階上昇と上限処理はCalc内で1回だけ行います。`ドラゴンスキン`はnative修正により、ノーマル技だけをドラゴンへ変換・強化し、他タイプの技を強化しません

4技のpatchは、CCの実行経路が同等のnative metadataを消費するようになった時点で該当entryを個別に撤去します。Gen0だけの対応ではGen9用patchを撤去しません。通常タイプ上書きと特性無視のpatchも、それぞれ同等のnative対応を確認して撤去します。

#### 味方特性の対応範囲

ダブルバトルの味方カードから計算へ反映する特性は、`わざわいのつるぎ`、`わざわいのたま`、`わざわいのおふだ`、`わざわいのうつわ`、`フラワーギフト`、`バッテリー`、`パワースポット`、`はがねのせいしん`、`フェアリーオーラ`、`ダークオーラ`、`オーラブレイク`、`プラス`、`マイナス`です。`フレンドガード`は、攻撃カードの状況条件から指定します。操作方法は[使い方ガイドの仮想敵シナリオ](https://championcreator.suisui-swimmy.com/guide/#scenarios)を参照してください。

#### 通常タイプとテラスタル

通常タイプの手動指定は、技が成功してタイプが変わった後の状態を入力する機能です。`Build.typeOverride`で1〜2個の通常タイプと任意の追加タイプ（くさ／ゴースト）を分け、adapterからCalcの`typeOverrides` / `addedType`へ渡します。タイプ相性、タイプ一致補正、無効化、接地判定、HPイベントと探索の最終再評価は同じCalc経路を使います。種族名・種族値・フォームのcanonicalは変更しません。指定した通常タイプはForecastによる自動タイプ推定より優先します。

テラスタル中はステラを含めて追加タイプを計算から除外します。通常タイプの手動指定はテラスタル前のタイプとして保持し、通常テラスの防御タイプはテラスタイプを優先します。設定をオフにしたときに比較できるよう、保存データには追加タイプを残します。タイプ変更技の成否・発動順・タイプ変更が禁止されるポケモン等は自動判定しません。通常タイプにステラ・不明タイプ、重複したタイプ、4個以上のタイプは指定できません。

入力・保存上の通常タイプと追加タイプは保持したまま、上記の計算時状態へ変換します。保存互換性は[保存形式](#保存形式と互換性)、入力操作は[画面仕様](#入力状態とレスポンシブ対応)を参照してください。

#### 威力指定と現在HP依存技

- `威力` 欄と計算結果には、タイプ一致・相性・持ち物・特性などを掛ける前に、その条件での `@smogon/calc` 計算で使った実効基礎威力を表示します。現在HP依存技は閉じたロック中に自動再計算し、ロックを外すと任意威力を直接入力できます。素早さ・体重・状態などから決まる技、連続技、固定ダメージ技、変化技も区別します

- アプリだけでは推測できない戦闘中条件を持つ `ゆきなだれ`、`きまぐレーザー`、`おはかまいり`、`ふんどのこぶし`、`りんしょう`、`はきだす`、`じだんだ`、`やけっぱち` は、合法な威力候補を `▲ / ▼` で切り替えられます。詳細ポップオーバーでは条件名の確認と任意威力の指定もできます
- `ふくろだたき` は威力欄から参加ポケモンと攻撃順を指定し、各ポケモンの攻撃種族値から1ヒットごとの威力を自動計算します。各枠のロックを外すと個別の任意威力も指定でき、参加上限は使用者を含めてシングル3体・ダブル4体です

- 条件ステッパーと任意威力はこの節に列挙した8技で使用できます。加えて現在HP依存技は、ロック解除中だけ自動計算を止めて入力威力を使用し、再ロックすると自動計算に戻ります。それ以外は入力済み条件から `@smogon/calc` が決めた威力を読み取り専用で表示します

- `ふくろだたき` は入力した参加ポケモンだけが攻撃するものとして評価します。ひんし・状態異常による参加可否は自動判定しないため、実際に参加できるポケモンだけを追加してください

任意威力は1〜10,000の整数です。`ふくろだたき`の各ヒットは参加ポケモンの攻撃種族値から算出し、個別上書き時だけ指定威力を使います。技・HP依存判定の実装は[movePowerRules.ts](src/calc/movePowerRules.ts)、[moveHpMechanics.ts](src/calc/moveHpMechanics.ts)、[beatUp.ts](src/calc/beatUp.ts)を参照してください。

### HPイベントの評価

- 定数ダメージは `@smogon/calc` の直接ダメージへ混ぜず、Champions HPルールと順序付きHPイベント評価層で処理します
- 現在対応する選択式HPイベントは `いのちのたま反動`、`すなあらし`、`どく`、`もうどく`、`やけど`、`ステルスロック`、`まきびし`、Champions版 `しおづけ`、`オボンのみ`、`たべのこし`、`ゴツゴツメット`、`さめはだ／てつのトゲ` です
- `ステルスロック` / `まきびし` → 直接攻撃 → 明示したヒットごとの接触反動・`オボンのみ` → 明示した`いのちのたま` → ターン終了時の天候 → 状態異常 → `しおづけ` → `たべのこし` の順でHPを更新します
- `もうどく` は開始段階を1〜15、`まきびし` は層数を1〜3で指定できます。`オボンのみ` は連続技の各ヒット後にも判定し、同じシナリオ内では1回だけ発動します
- HPイベントの対象は効果から自動決定し、`いのちのたま反動`・接触反動は技使用者、それ以外の選択式効果は技の被弾側へ適用します
- 現在HP依存ダメージ・威力は選択した技から自動判定し、各攻撃時点のHPで直接ダメージを再計算します

- タイプ相性・地面にいるかの判定には `@smogon/calc` の世代データと判定を使い、`マジックガード`、`ポイズンヒール`、`たいねつ`、`あつぞこブーツ` など主要な無効化・変換も反映します

効果の対象・発動タイミング・頻度は利用者が自由に組み合わせる値ではなく、[hpEventRuleDefinitions](src/calc/hpEventRules.ts)の定義から決まります。現在HP依存技の補足は選択式イベント一覧とは別に表示します。

`しおづけ`はCCで採用するChampions用ルールとして、最大HPの通常1/16、みず・はがね1/8を切り捨て、最低1ダメージで評価します。これは[実装](src/calc/hpEventRules.ts)と[丸めの回帰テスト](src/calc/hpEventRules.test.ts)で確認できるアプリの仕様です。リポジトリにはゲーム公式資料へ辿れる出典記録がなく、公式確認済みとは扱いません。

#### 評価単位と未対応のHP変化

- HPイベントは選択した効果が存在する前提で評価します。持ち物・状態・天候が入力と一致しない場合はUIで警告しますが、自動削除はしません。技失敗、`ちからずく`、持ち物の消費済み状態など、発動条件すべての自動推測は未対応です
- 現在は完了した通常技1回を1ターン境界として扱います。通常技の複数回指定では砂ダメージも各回に発生し、連続技では全ヒット後に1回だけ発生します。同一ターン内の複数行動をまとめる明示的なターン指定は未対応です
- 技固有の使用者側反動、HPコスト、使用者ひんしは通常の耐久・火力ラインへ自動適用しません。調整対象と仮想敵が交互に技を使い、どちらかのひんしで後続行動を止める完全な対戦進行は未対応です
- `ふんか`・`しおふき`・`ドラゴンエナジー`・`じたばた`・`きしかいせい`・`ハードプレス`など、対応済みの現在HP依存技は各攻撃時点のHPで再計算します。現在HPで発動条件が変わる全特性・全持ち物までを完全なバトル状態として再現するものではありません

- 調整対象のHPはシナリオ内で継続し、明示追加した`いのちのたま`・接触反動などの技使用者側HP変化も同じ攻撃カード内では継続します。別の攻撃カードを同じ技使用者として結び付ける指定は未対応です

- `まきびし` の地面判定は現在UIで指定できる条件の範囲です。`じゅうりょく`、`うちおとす`、`ねをはる` など未入力の戦闘中状態までは扱いません
- 命中失敗そのものをシナリオ化していないため、`とびひざげり`などの失敗時反動は未対応です。`ニードルガード`、`ジャポのみ`、`レンブのみ`、`やどりぎのタネ`、`アクアリング`など、この節の対応一覧にないHP変化も未対応です

順序付き評価は[simulateHpSequence.ts](src/calc/simulateHpSequence.ts)を使い、[対応テスト](src/calc/simulateHpSequence.test.ts)で連続技、回復、天候・状態異常の順序、現在HPからの再計算を確認しています。ここでいう直接攻撃は、接触技だけを意味しません。接触反動は接触判定のあるヒットに限ります。

### 耐久条件・生存率・最厳条件

耐久調整では、1つの`H / B / D`候補を有効な全耐久シナリオへ評価します。`HB`と`HD`を別々に解いて合成しません。UI変換時には無効なシナリオを除外し、有効な耐久シナリオがない場合や、シナリオ内に有効な攻撃がない場合は探索を開始せず理由を返します。

各シナリオ内では攻撃カード順にダメージを積み上げます。カードごとの必要耐久回数は、それ以前の攻撃を含めた到達点へ変換し、その時点でHPが残る確率を求めます。必要回数に攻撃列が足りない場合は不合格です。HPイベント・現在HP依存がある場合はHPシーケンスを使い、それ以外はCalcのロールから累積ダメージ分布を求めます。シナリオ間でHPを引き継ぐ対戦進行ではありません。

合格条件は、各到達点の生存率が必要生存率以上であることです。浮動小数点誤差への許容値は`1e-12`で、画面で丸めた％を判定に使いません。シナリオ内の全到達点、さらに有効な全シナリオの合格が必要です。

`余裕`は「生存率 − 必要生存率」、`最厳条件`はこの余裕が最小となる条件です。単にダメージ最大の技や、生存率が最小のシナリオを示すものではありません。候補0件の場合は、最も合格に近かった不合格候補のボトルネックを失敗理由の手掛かりとして返します。

実装は[UI変換の`toScenarioHits` / `buildDefenceSearchInput`](src/ui/defenceSearchUi.ts)、[探索の`evaluateScenario` / `evaluateCandidate`](src/search/defenceSearch.ts)、[到達点・最終再評価のテスト](src/search/defenceSearch.test.ts)を参照してください。

### 火力ラインと固定SPの統合

火力調整は調整対象を技使用者、仮想敵を被弾側として扱い、指定回数の攻撃と明示したHPイベントの後に相手がひんしとなる確率（KO率）を求めます。直接ダメージだけの場合は相手HP以上のダメージをKOに数え、HPイベント込みでは回復・定数ダメージも含むHP分布から判定します。

技の参照能力ごとに、他能力のSPを予算へ含めて0〜32の合法範囲を調べ、指定KO率に届く最小SPを返します。通常は物理技がA、特殊技がCですが、ボディプレスはB、いのちがけはH、イカサマは相手Aを参照します。可変参照技ではA/Cの複数ラインを扱い、SPを変えても結果が不変なら`固定条件`として合否を返します。届かないA/Cラインの性格補正案は参考表示であり、自動適用しません。

通常の耐久探索の準備では、入力中のA/C/Sを維持し、H/B/Dを0とした基準から必要条件を算出します。火力調整は、同じカードに代替ラインがある場合に必要SPの組み合わせを比較し、能力別の必要量を最大値で統合します。そのA/Cを反映した基準で、入力済みS以上の合法なSPを順に調べ、すべての素早さ条件を同時に満たす最小のSを固定します。A/C/Sは入力済みSPを下回らない固定値、火力が要求するH/B/Dは最低SP条件として渡します。固定SPとH/B/D下限の合計が66を超える、または必要条件を両立できない場合は、統合できない理由を表示します。

この前処理はA/C/SとH/B/Dの全6能力を総当たりする同時最適化ではありません。火力の代替組み合わせは同じ必要配分をまとめ、必要SP順に最大32状態を保持して選びます。耐久探索の最終再評価対象は、その固定条件を持つBuildと耐久シナリオです。

実装は[offenseAdjustment.tsの`calculateOffenseAdjustment`](src/search/offenseAdjustment.ts)、[UI変換の`resolveIntegratedOffenseRequirements` / `buildIntegratedDefenceSearchInput`](src/ui/defenceSearchUi.ts)。参照能力・KO判定は[火力テスト](src/search/offenseAdjustment.test.ts)、予算統合は[UI変換テスト](src/ui/defenceSearchUi.test.ts)を参照してください。

### 素早さラインの条件

素早さ調整では、調整対象の最終Sと相手の最終Sを比較します。条件は、全体へ適用する `共通S条件`、相手側へ適用する `相手S条件`、調整対象側へ適用する `調整対象S条件` に分かれています。

- `共通S条件` は、ルール、天候、フィールド、行動順（通常／トリックルーム）を指定します。トリックルームと、おいかぜ（両側）は同時に指定できます
- `相手S条件` と `調整対象S条件` は、それぞれの状態異常、道具倍率、特性倍率、おいかぜを個別に指定します。まひは通常Sが1/2になり、状態異常時の`はやあし`はSが1.5倍になります
- `任意S値` は相手の最終Sを直接入力する条件です。この場合、相手ポケモンのS能力や相手S条件は使わず、調整対象側と共通S条件だけを反映します

最終SはCalcの素早さ計算経路で求め、通常順では現在SPから増やす方向、トリックルームでは現在SPから0へ減らす方向で、指定差を満たす最初のラインを返します。`抜ける` / `同速` / `届かない`を区別し、同速を確定抜きとして扱いません。現在の性格で届かない通常順の性格補正案は参考表示です。

道具倍率・特性倍率は通常`自動`で、手動の`2` / `1.5` / `0.5`を選ぶと、そのカテゴリの自動補正を置き換えます。これは最終Sへの数値上書きで、特性の発動条件や丸め順まで完全に再現するものではありません。`かるわざ`・`スロースタート`の発動状態、`こだいかっせい`・`クォークチャージ`でSが上昇する状態を直接指定する専用UIは未対応です。

実装と判定例は[speedAdjustment.ts](src/search/speedAdjustment.ts)と[対応テスト](src/search/speedAdjustment.test.ts)を参照してください。通常の耐久探索へ渡すSは前節の固定SP統合に従い、単独のSライン適用とは分けて扱います。

単独Sラインの提案と、指定配分の合否判定は分離しています。通常の耐久探索では入力済みSを自動で減らさず、トリックルームの上限を超えている場合や通常順とトリックルームの条件が両立しない場合は、候補生成を止めて現在S・必要なS条件を表示します。Sを減らせば達成できる条件には変更先のSPも示します。入力済みSを変更するか、単独Sラインを明示的に適用してから再計算してください。統合の実装と回帰テストは[defenceSearchUi.ts](src/ui/defenceSearchUi.ts)、[defenceSearchUi.test.ts](src/ui/defenceSearchUi.test.ts)を参照してください。

正規化したS条件はWorkerへ渡し、候補ごとの実配分を`evaluateSpeedCondition`で評価します。探索中・最終再評価ともに未達候補を除外し、候補詳細のS配分・実数値・PASSはその評価結果を表示します。単独調整で求めた別配分の提案値は候補の合否や詳細に流用しません。

### 候補の列挙・絞り込み・再評価・順位付け

1. 有効な耐久技の参照先とHPイベントから必要な耐久軸を求め、火力由来のH/B/D下限の軸も含めます。通常の物理だけならH/B、特殊だけならH/D、混在・可変参照なら必要な両軸を扱います。技の分類は[moveStatReference.ts](src/domain/moveStatReference.ts)を使います。
2. 検索する軸の各SPを0〜32、固定分を含む総SPを66以下として、耐久SPの合計が小さい順に列挙します。検索しない能力は渡されたBuildの値を維持します。
3. 火力由来の最低SP未満を除外し、各候補を全耐久シナリオと全S条件に評価します。合法SPとすべての条件を満たした候補だけを蓄積します。
4. `finalizeDefenceSearchResults`で候補を再び全耐久シナリオと全S条件へ評価し、不合格と最低SP未満を除外してから順位を付けます。通常画面は`maxResults: null`を指定し、検索対象の全合格候補を返します。内部APIで件数上限を指定する場合は、その上位候補を再評価します。

`推奨順`は、H/B/D使用SPの少ない順、残りSPの多い順、最厳条件への余裕の大きい順、HのSPの大きい順です。画面の並び替えは候補の合否を変更しません。実装は[defenceSearch.ts](src/search/defenceSearch.ts)、全件・軸絞り込み・不合格除外は[対応テスト](src/search/defenceSearch.test.ts)を参照してください。

#### 耐久指数

- 候補一覧は、`総合耐久指数=HBD/(B+D)`、`物理耐久指数=H*B`、`特殊耐久指数=H*D` でも並び替えられます。H/B/D は候補適用後の実数値（H=`maxHP()`、B=`stats.def`、D=`stats.spd`）を使い、SP値の積ではありません

- 3つの耐久指数はシナリオ固有のダメージ、タイプ相性、特性、持ち物、HPイベントを含まない並び替え用の補助指標で、検索の合否判定やシナリオ評価を置き換えません

### 残りSPで耐久最大化

- `残りSPで耐久最大化` は、固定するA/C/SのSPと火力・素早さ調整の必要条件を反映し、残る予算をH/B/Dへ再配分します。現在の物理・特殊耐久指数を両方維持できる候補を、総合耐久指数順に最大50件返します。性格変更は `性格変更` にチェックを入れた場合だけ検討し、火力条件が要求するA/C実数値とH/B/D下限を保護します。Sは各候補の配分・性格と状況補正で全S条件を再評価し、通常順の下限・トリックルームの上限を満たす候補だけを返します。仮想敵への耐久判定を保証する機能ではなく、適用後の合否は通常の計算で確認してください

性格候補を含む合法な配分を評価し、丸め前の総合耐久指数で順位を決めます。同点でも配分・性格の異なる候補を残し、返却上限は同点を含む50件です。条件によって50件未満になります。実装は[maximizeRemainingBulk.ts](src/search/maximizeRemainingBulk.ts)、SP・実数値保護と上位50件は[対応テスト](src/search/maximizeRemainingBulk.test.ts)を参照してください。

### Workerと結果のライフサイクル

耐久探索と耐久最大化はWeb Workerで実行します。通常探索は`start`に対して`progress`、`partialResult`、`complete`または`error`を返し、`cancel`で協調的に中断します。一定件数ごとに制御を返してキャンセルを確認し、取り消したリクエストの完了結果を採用しません。

`partialResult`は探索済み範囲の上位プレビューで、通常画面では最大20件です。併送する合格件数はその時点の累計であり、プレビュー表示件数とも最終件数とも区別します。`complete`の件数は最終再評価後の全合格件数です。耐久最大化は進捗と完了結果を返す別のリクエストです。

入力変更、ボックスや共有データの読み込み、再計算、画面破棄では進行中の探索を中断し、古い結果を破棄します。clientとUI reducerは`requestId`が現在の要求と一致するメッセージだけを反映します。候補の`適用`は入力SP（耐久最大化では選んだ性格も）を更新し、計算結果自体は保存しません。

`性格変更`のチェックだけでは入力中の性格を変更せず、次の耐久最大化の探索へ反映します。耐久最大化の候補表示中に同じボタンを押すと閉じ、次に押すと再計算します。入力変更時はその候補も破棄します。通常探索・耐久最大化の候補一覧、計算結果、Worker stateは保存・同期対象外です。

実装は[Worker](src/worker/defenceSearchWorker.ts)、[client](src/worker/defenceSearchWorkerClient.ts)、[UI reducer](src/ui/defenceSearchUi.ts)、[Appの入力変更・読み込み処理](src/App.tsx)。中断、古い応答、途中20件と最終全件の差は[Workerテスト](src/worker/defenceSearchWorker.test.ts)を参照してください。

### metadataと計算対応

フォーム・特性などのmetadataは明示manifestとvalidatorでCalcより先に扱う場合があります。`metadata-supported`はデータとして存在すること、`engine-supported`は利用できるエンジン経路があること、`calculation-supported`はその値とmechanicsを実際の計算経路が消費することを区別します。入力候補へ表示されることだけで、ゲーム内実装やすべての特殊効果への対応を保証しません。

メガシンカ後の特性は、全97フォームを明示manifestで管理し、確定88フォームではそのフォーム固有の特性を自動入力します。現行データで未確定のメガヒードラン、メガダークライ、メガジガルデ、メガマギアナ、メガゼラオラ、メガシャリタツ（canonicalでは9フォーム）は自動入力せず空欄を維持し、ドロップダウンにはメガシンカ前の特性候補を表示します。Calc更新や公式発表時にmanifestを監査し、特性が確定したフォームから通常の自動入力へ移します。

#### ダイマックス・キョダイマックス

通常ダイマックスは別speciesではなく、計算条件のフラグです。現在の固定Calcと生成catalogには`-Gmax`のcanonical speciesがないため、キョダイマックスフォームや専用効果は受け付けません。専用効果を独自のダメージ後補正で補うこともありません。将来対応する場合は通常ダイマックスとは別のmechanicsとして監査が必要です。

### 使用率データの取得・生成・validation

入力補助の参照元は[Pokemon Champions Battle Data](https://championsbattledata.com/)の`Current`です。[generate-champions-usage.mjs](scripts/generate-champions-usage.mjs)が集約APIと提供元のbulk ZIPを取得し、技・特性・持ち物、ポケモン順位、上位10件の性格使用率を同じ形式・フォームへ正規化します。性格CSVはAPIが示すパスに対応付け、ZIPに該当ファイルがない場合だけ、同じ提供元のAPI指定`Current` CSVを直接取得します。別フォーム・旧名・過去シーズンのCSVから推測して補いません。

ポケモン順位は提供元の`Current`各形式における`position` / `column_position`を、使用率schema v1のoptional `pokemonRank`として生成・検証します。技などの行内`rank`や別形式・過去データから順位を補完しません。順位を持つ既存の日本語入力候補だけを使い、フォームの順位を推測せず、同一canonicalの表示別名は重複させません。提供元で集約されるギルガルドは初期状態のシールドフォルム1件として選択できます。旧使用率JSONは引き続き読み込め、share / box schemaには順位を保存しません。

性格の不正な％、範囲外値、重複・衝突、不正な展開パスはvalidation errorです。直接取得したCSVにもZIP内と同じ検証を適用します。個別の不明候補、直接取得でも404となる欠損CSVは警告して該当データを欠落として扱い、通信失敗・404以外のHTTPエラーは生成を停止します。ZIPに利用可能な性格データがない、または片方の`Current`形式全体で利用可能な性格データがない場合も、直接取得の成否にかかわらず生成を停止します。変換と失敗条件は[generatorテスト](scripts/generate-champions-usage.test.mjs)、配信JSONの受け入れは[使用率schema](src/usage/schema.ts)と[テスト](src/usage/schema.test.ts)を参照してください。

出力は`public/data/champions-usage-current.json`で、git管理せずローカルまたはGitHub Actionsで生成します。schema v1の旧JSONも読み込め、任意項目の性格使用率やポケモン順位がない場合は未取得として扱います。ブラウザは生成済みJSONを読み、使用率取得のために提供元をruntime scrapingしません。画面の候補順・初期入力・欠落表示は[入力サジェストと性格の使用率](#入力サジェストと性格の使用率)を参照してください。

[Pages workflow](.github/workflows/deploy-pages.yml)は次の失敗経路を持ちます。

- 定期実行は1日1回確認し、`dataVersion`が公開済みと同じならbuild・公開を省略します。生成に失敗した場合はジョブを失敗させ、直前に正常公開できたPagesを維持します。
- push／手動実行で生成に失敗した場合は、公開中JSONを取得・検証してfallbackに使います。それも利用できなければ、schemaに適合する空のランキングでbuildします。
- 提供元とデータ更新日はアプリのフッターへ表示します。取得不能・未掲載は使用率0%を意味しません。

#### 使用率専用のFloette正規化

対応表の正は[`champions-usage-pokemon-mappings.json`](src/data/overrides/champions-usage-pokemon-mappings.json)です。使用率APIの旧`floette`を`Floette-Eternal`（ID `floetteeternal`）へ対応付ける根拠、確認日、API版、確認済み6能力を保持しています。判定値はLv50 / IV31 / EV0 / 無補正のH149・A85・B87・C145・D148・S112で、同一性の確認だけに使い、Calcの入力へ流用しません。

- 旧名だけのAPIでは、対応表の確認済み能力値を検証して`floetteeternal`へ正規化します。
- 旧名と新名の両方がある場合は、旧名の確認済み能力値が一致し、旧名に`Current`集計も`Current` CSVもなく、一意な新名に現在データがある場合だけ、履歴専用の旧名を生成対象から除外します。
- 元APIで両名に現在データがある、IDが重複する、新名側の現在データがない、確認済み旧名の能力値が変わる場合は生成を停止します。上書き・合算・配列順による選択はしません。
- 旧v1公開JSONのfallbackも同じ対応表で読み込み時に正規化します。両キーや同一canonicalの重複はvalidation errorです。補正を使う生成物の`dataVersion`には対応表のdigestを含めます。
- ポケモン順位、技・特性・持ち物、bulk CSVの性格使用率に同じ選択処理を使います。メガフラエッテは進化前ownerの解決によって正規化済み`Floette-Eternal`を参照します。
- 適用範囲は使用率だけです。Calcの種族値・フォーム、通常検索の`Floette`＝`フラエッテ あかいはな`、保存済み入力は変更せず、未進化ポケモンを一律に除外・置換しません。

対応表の`nativeTransition`は、2026-09-15確認時に旧名が9月11日までの履歴、新名が9月12日以降と`Current`を持っていた観測記録です。この日付を将来のAPI状態の保証には使わず、生成のたびに上記条件を検証します。生成停止時の配信は前節の定期実行／push・手動実行それぞれのfallbackに従います。

### ダメージデバッグ用のみがわり

ポケモン名に「みがわり」を入力すると、タイプなし（すべての攻撃タイプを相性上1倍で受ける）のデバッグ用ポケモンを選べます。調整対象・仮想敵の両方で使え、[人形画像](public/assets/debug/substitute.png)を表示します。技の「みがわり」や身代わり状態の再現ではありません。

Lv.50・個体値31・SP0・無補正では、実数値がHP300、A/B/C/D/Sは100になります。種族値はH225、その他は80で、レベル・個体値・SP・性格による増減は通常どおり反映します。固有の特性はなく、デバッグ用の体重は0kgとしてCalcの通常ルールへ渡します。持ち物・特性・天候・テラスタルなどを別途指定した場合、その補正は通常どおり適用します。

定義・確認日は[`debug-pokemon.json`](src/data/overrides/debug-pokemon.json)を正とし、入力候補と特性をgeneratorから生成します。計算ではcanonical `Substitute`に対して`Pokemon.overrides`で上記種族値とCalc内部の等倍タイプ`???`を渡し、通常の実数値・直接ダメージ・HPイベント・探索経路を使います。内部タイプは入力候補へ公開せず、画面には「タイプなし」と表示します。保存形式は既存schemaを使います。

## 入力・画面表示の仕様

操作手順は[使い方ガイド](https://championcreator.suisui-swimmy.com/guide/)を参照してください。ここでは、表示と入力状態・計算条件の対応を定義します。

### 入力サジェストと性格の使用率

使用率の取得・正規化・欠損・fallbackは[データ仕様](#使用率データの取得生成validation)を参照してください。使用率は入力補助に使い、計算結果へ直接補正を掛けません。

技・特性・持ち物の入力候補は、Pokemon Champions Battle Data が提供する `Current` の使用率データをもとに並び替えます。ヘッダーの「シングル」「ダブル」を切り替えると、サジェスト基準に加えて、現在の全シナリオ・全攻撃カードの `状況条件 > ルール` を同じ形式へ一括変更します。各攻撃カードのルールはその後も個別変更でき、個別変更からヘッダーへは逆同期しません。次にヘッダーを切り替えた場合は、個別変更を含む現在の全攻撃カードへ再度一括適用します。

選択したサジェスト基準だけが同じブラウザに保存されます。条件JSONやボックスから読み込んだルールは、読み込み時にはヘッダーの形式で上書きせず、次にヘッダーを操作した時だけ一括変更します。ダブル4体の `ふくろだたき` をシングルへ一括変更した場合は、既存のルール変更と同じく参加上限3体へ整理されます。

ヘッダーのサジェスト基準の初期値はシングルです。

技・特性・持ち物は、使用率データに掲載された候補を先頭へ移し、未掲載候補は五十音順で残します。順位や使用率そのものは表示せず、候補の並び順と、ポケモン選択時の初期入力に反映します。メガシンカ後のポケモンでは、X / Y / Zを含め、一意に定まるメガシンカ前のポケモンへ集約されたデータを、これらの候補順・初期入力と性格の使用率表示に参照します。

技・特性・持ち物の `>` は、入力済みの文字で絞り込まずに使用率順の候補を開きます。入力欄を編集すると前方一致検索へ切り替わり、それぞれ使用率順への並び替え後に最大40件を表示します。特性のメニューはそのポケモンの特性候補を使い、使用率データがない場合は既存の候補順を維持します。調整対象、各調整の仮想敵、ガイドのチュートリアルで共通です。メニューを開いても現在値は変更せず、Tabでは候補を確定せずに次の操作へ移ります。

すべてのポケモン名入力欄の `>` を押すと、ヘッダーで選択中のシングル / ダブルに応じたポケモン使用率順のリストを開きます。入力済みの名前によらず先頭から表示し、掲載された候補はスクロールで最後まで選べます。文字を入力すると名前検索へ切り替わり、順位のないポケモンも検索できます。調整対象、各調整の仮想敵、「ふくろだたき」の参加ポケモン、ガイドのチュートリアルで共通です。上下キーで候補移動、Enterで選択、Escapeで閉じられます。ランキング表示中はHome / Endで先頭 / 末尾へ移動し、Tabは選択せず次の操作へ移ります。使用率ランキングが未取得の場合は、その状態を表示して名前検索を案内します。

使用率データの取得後にポケモンを候補から選ぶと、選択中のシングル / ダブルで最上位かつ、そのポケモンの有効な入力候補に存在する技・性格・特性・持ち物を自動入力します。技は変化技を除外し、ランキング内で最上位の物理技または特殊技を入力します。確定済みのメガシンカ後の特性だけは、使用率データの取得状況や順位に関係なく、そのフォームで唯一の特性を入力します。調整対象では性格・特性・持ち物を入力し、火力調整カードの技は攻撃者である調整対象の使用率を使います。耐久調整カードでは攻撃側の4項目を入力し、火力・素早さ調整の仮想敵では技を除く3項目を入力します。空欄または、現在値が直前のポケモンにおける同形式の1位と一致する欄だけを次のポケモンの値へ更新し、それ以外の手動入力は残します。使用率データがない項目や、ランキング内にそのフォームで有効な候補がない項目は空欄のままです。ランキング内に有効な物理技・特殊技がない場合、技は空欄のままです。ヘッダーの形式やシナリオの調整種別を切り替えただけでは既存入力を変更せず、その後にポケモンを候補から選んだ時点で新しい基準を使います。

メガシンカ可能なポケモンでは `メガ候補` から姿を選ぶと、使用率1位の持ち物より優先して対応するメガストーンを持ち物へ自動入力します。メガシンカを解除したときは、現在の持ち物がその姿の対応石と一致する場合だけ空に戻し、手動で変更した別の持ち物は残します。対応するメガストーンを持たないメガレックウザでは、通常どおり使用率データを参照します。

メガフォームごとの確定／未確定特性と自動入力の範囲は[metadataと計算対応](#metadataと計算対応)を参照してください。

性格は、調整対象と各攻撃カードの5×5能力補正表へ実使用率の濃淡を表示します。画面上には詳細な％・順位を追加表示せず、各セルのARIAラベルへ性格、能力補正、選択中のシングル／ダブル使用率、順位を含めます。提供データは上位10件のため、掲載されていない性格は `0%` と扱わず、ARIAラベルでは `上位外／データなし` と区別します。使い方ガイドのチュートリアル画面では、技・特性・持ち物の候補順にダブル使用率データを使い、性格表は使用率表示なしを維持します。

### SP・HP・威力・結果の表示

SP配分バーは、性格上昇補正で無補正時より実数値が多く伸びる位置を赤、性格下降補正で伸びが少なくなる位置を青で示し、選択中のレベルにも追従します。

H行の`HP基準`は`2n / 3n / 4n / 6n / 8n / 10n / 16n / 50n`から1つ選びます。

H行の`HP基準`は通常時HPをSP 0〜32で実計算し、選択した基準倍数だけを表示します。`−1 / ＋1`などのオフセットは実数値を見て利用者が決めます。同じHPが続く場合は最小SPだけを目安にし、SP0も表示対象です。

レベルのロックボタンと解除中の入力、操作可能な威力欄・条件ステッパーは通常のTab順で到達できます。読み取り専用の威力表示は操作ボタンと区別します。実装は[App.tsxの`LevelLockField` / `MovePowerField`](src/App.tsx)、Tab順の契約は[App.test.tsx](src/App.test.tsx)を参照してください。威力の意味と指定できる技は[計算仕様](#威力指定と現在hp依存技)にまとめています。

素早さの手動倍率には`手動`と表示します。選択中の持ち物・特性に実際の自動S補正がある場合は、手動倍率で置き換えられる元入力も識別できるように表示します。

- 耐久・火力のダメージ詳細は、Calcの説明文から両者の配分をSPへ変換し、`C32+（Cランク+1）`や`H20 / D0（Dランク+1）`と表示します。末尾の`+` / `-`は性格補正、括弧内はCalcが計算に反映したランクです。レベル付き・HP配分だけの説明文にも対応し、ボディプレスはB、イカサマは受け側Aの参照を明示します。表示変換でダメージロールや合否は変更しません

通常候補一覧は20件ずつ表示し、`推奨順`、`使用SP`、`残りSP`、`余裕`、各耐久指数、H/A/B/C/D/Sで昇順・降順を選べます。直接ダメージ、適用威力、定数ダメージ・回復の内訳は分けて表示します。並び替えとページングは計算済み候補の表示操作です。

最厳条件には条件名と余裕を表示し、読み上げでは`最厳条件: `を付けます。条件名と火力・素早さラインの説明は省略せず全文を表示します。

耐久最大化では、最上位候補の順位・性格・総合耐久指数とH/B/Dの実数値・SPを表示し、候補を適用できます。括弧内の数値はSPを表し、指数表示は総合耐久指数に絞ります。`候補を比較`はPCのダイアログで20件ずつ、720px以下の下シートで5件ずつ表示します。候補破棄や性格変更の反映時点は[ライフサイクル](#workerと結果のライフサイクル)に従います。

### 入力状態とレスポンシブ対応

- 仮想敵の入力は表示順にTab移動できます。素早さ調整では技・威力の入力を非表示にしますが、値は保持し、耐久調整・火力調整へ戻すと再表示します。スマホの素早さカードには相手のポケモン名を表示し、未入力なら「未設定」とします。
- スマホで無効化したシナリオは、接続線上の操作ができなくなります。シナリオカードは残り、再有効化できます。
- 調整対象と仮想敵のテラスタイプは、文字検索または`>`から、ステラを含む全19タイプを選べます。

通常タイプは最大3個を表示します。初期状態はロックしてポケモン・フォームに追従し、解除するとタイプ1・タイプ2と、くさ／ゴーストの追加タイプを手動指定できます。タイプ画像は`public/assets/types/`の表示専用アセットで、runtimeは`others/`に依存しません。

本体のフッターでは用途と基本操作を表示し、「計算方法と検証について」から計算の基盤・検証・制限へのリンクを確認できます。説明は初期HTMLに含まれ、JavaScript起動前も開閉できます。

入力操作にはフォーカス表示を持ち、ロック・候補・popover・sheetの操作をhoverだけに限定しません。具体的な寸法・描画は[src/styles.css](src/styles.css)と対応テスト、共通の操作サイズ・検証方針は[AGENTS.md](AGENTS.md)を参照してください。

## 保存・認証・同期

未ログイン時と初回統合を保留している間はブラウザ内保存を使用します。Googleログイン後に初回統合を完了すると、ボックスと下書きがアカウントの識別子（UID）単位の保存先へ切り替わります。同期障害時もブラウザ内保存とJSONバックアップを利用でき、ログアウト・アカウント切替でゲスト領域とUID領域を混ぜません。

### 保存形式と互換性

| 対象 | 現行形式・読み込み |
| --- | --- |
| 調整対象＋シナリオの入力条件 | `ShareStateDocument` schema 13。`target`と`scenarios`を保存し、schema 1〜13を既存parserで読み込む |
| 調整対象ボックス／バックアップ | 外側のschema 1。各保存の入力payloadは条件schemaへ正規化する |
| 仮想敵ボックス／バックアップ | 外側のschema 1。シナリオ入力を条件parserと共通の経路で読み込む |
| ブラウザ・クラウド下書き | 入力条件を保存する。計算結果、候補一覧、Worker stateを含めない |
| 同期用envelope | schema 1。入力payloadとrevision・mutation ID・server timestampを分離する |
| URL共有 | 独立したwire形式`s1`。条件schema 13の省略値を固定する（[URL共有](#urlで調整を共有する)） |

条件schema 13は通常タイプの手動指定を保存し、v1〜v12では自動設定（ロック中）へ移行します。調整対象・仮想敵ボックス、バックアップ、ブラウザ下書き、同期payloadは既存parserを共有します。旧形式の不足項目は版ごとの移行規則に従い、未知のschemaを空データとして読み込みません。

主な互換処理は、旧トップレベル`offenseAdjustment`を再出力しないこと、威力欄のない旧形式を自動威力とすること、旧`ふくろだたき`を使用者だけの参加列へ移すことです。レベルmodeのないv1〜v9は50ならロック・50以外なら手動、旧S条件はv11の行動順と両側条件へ変換します。canonicalの補助情報はv12以降、通常タイプ上書きはv13以降を受け付けます。現在形式での不正なレベル・mode・タイプ指定などはエラーです。

保存できたことと、resolver・計算条件が完成していることは別です。空欄や旧CAP等の未解決入力は編集用に残し、計算時に解決状態とSP制約を確認します。破損JSON、未知schema、個別payloadの問題を区別し、読み込めないクラウド1件のために正常な一覧を空にしません。細部は[shareState.ts](src/ui/shareState.ts)と[移行テスト](src/ui/shareState.test.ts)、両[ボックス](src/ui/boxStorage.ts)の[parser](src/ui/enemyBoxStorage.ts)を参照してください。

<a id="ブラウザ内保存"></a>

### ブラウザ内保存・ボックス

入力中の調整対象とシナリオは、変更が止まってから約0.75秒後に、ボックスとは別の「作業中の下書き」として同じブラウザへ自動保存されます。次回起動時に下書きが見つかっても自動では適用せず、`下書きを復元` / `下書きを破棄` を選べます。

下書きに保存するのは入力条件だけです。計算結果、候補一覧、Workerの進行状態は保存しません。ガイド内のチュートリアルも保存対象外です。ブラウザの保存容量不足などで保存できない場合は、画面にエラーと再試行操作を表示します。

調整対象ボックスには、調整対象、シナリオ、火力ライン、素早さラインなどの入力条件をまとめて保存できます。仮想敵ボックスには、調整対象を変えずに、よく使う仮想敵シナリオだけを保存できます。

調整対象ボックスへ現在の条件を保存または上書きすると、その内容を確定保存として扱います。ボックス保存の成功後に作業中の下書きを削除し、次に入力を変更するまで`ボックスに保存済み`と表示します。ボックスから保存を読み込むと、その入力条件を次の下書きとして自動保存します。空スロットを読み込んだ場合は、作業中の下書きも破棄します。

仮想敵ボックスへの保存だけで作業全体を確定済みにしたり、調整対象の下書きを消したりはしません。

#### 既定サンプルと白紙初期状態

ボックスの「調整例：メガリザードンY」、チュートリアル、計算例は[`adjustment-example.json`](src/data/presets/adjustment-example.json)を共通の入力とします。レベル50・ひかえめ・ひでり・リザードナイトＹで、いじっぱりA32ガブリアスのダブルダメージ「いわなだれ」を90%以上耐え、H2イダイトウ♂を「ソーラービーム」で確定1発、ようきS32イダイトウ♂を確定抜き+1（実数値差2）にします。完成配分はH4 / A0 / B27 / C10 / D0 / S25、チュートリアルは同じ条件のSP未配分から開始します。未編集の旧ブラウザ内サンプルは同じ保存IDで更新し、変更・複製済みの保存と削除済みサンプルの状態を保持します。同期の初回移行でも新旧の未編集サンプルと利用者の変更を区別します。

サンプルは一度だけ用意する削除可能な保存です。起動時の作業入力へ自動適用せず、利用者が削除したサンプルを再生成しません。

### 起動・復元の順序

起動時はログイン状態と保存先を確認し、同期を利用している場合はボックス・クラウド下書きの初回確認が終わるまで作業画面を表示しません。その後、同じアカウントのこのブラウザの下書きを確認し、復元・破棄の選択へ進みます。通常の自動同期や画面へ戻ったときの同期では、作業画面を止めません。起動の確認が8秒以上かかる場合、オフライン、同期エラーの場合は再試行できます。同じアカウントの同期用ブラウザ内保存を利用できる場合は、`このブラウザに保存済みのデータで続ける`も選べます。続行後の同期完了で起動画面や下書き確認を再表示しません。ログイン状態が未確定、保存先が別アカウント、同期用ブラウザ内保存が利用できない場合は、この続行操作を表示しません。

### 初回統合

Googleログイン後、ブラウザ内の既存ボックスとクラウド側の保存を初めて結び付けるときは、保存データの扱いを選びます。選択肢は`統合` / `クラウドを使用` / `このブラウザを使用` / `あとで決める`です。

- `統合`: 同じID・同じ内容は1件にまとめ、同じIDで内容が異なる保存は競合コピーとして両方を残します
- `クラウドを使用`: クラウド側の保存をアカウントの保存内容として使います
- `このブラウザを使用`: このブラウザの保存をアカウントの保存内容として使います
- `あとで決める`: 統合を保留し、ブラウザ内保存を維持します

統合が成功するまでは、既存の`championcreator.box.v1`、`championcreator.enemy-box.v1`、既定サンプルの削除状態を残します。失敗しても既存データやJSONバックアップを失いません。未変更の既定サンプルは重複させず、ユーザーが削除したサンプルを勝手に復活させません。

初回統合の対象は、調整対象ボックスと仮想敵ボックスに保存した入力条件です。計算結果、候補一覧、Workerの状態、チュートリアル、作業中のクラウド下書きは含めません。

### ボックス同期

Googleログイン後に初回統合を完了すると、調整対象ボックスと仮想敵ボックスをアカウントの識別子（UID）ごとに同期します。作成、上書き、名前変更、複製、削除、読み込み、バックアップの書き出し・読み込みが対象です。

保存操作は、まずこのブラウザへ確定します。その後、未送信操作を順番に保持するキュー（`outbox`）へ追加し、クラウドデータベース（Firestore）へ送ります。同期は起動時、画面へ戻ったとき、オンライン復帰時、ボックス操作後、`今すぐ同期`を選んだときに行います。ネットワーク、権限、利用上限などの理由でクラウド同期に失敗しても、ブラウザ内の保存とJSONバックアップは利用できます。

通常の削除では、元の保存内容を残したまま削除済みと記録します（`tombstone`）。同じ保存を複数のブラウザで変更した場合や、更新と削除が重なった場合は、一方を自動採用せず`競合あり`として両方を保持します。クラウド上の1件が破損していても、その保存だけを問題として分離し、正常な一覧を空にしません。

### ブラウザ別クラウド下書き

Googleログイン後に初回統合を完了すると、作業中の下書きもブラウザごとにクラウドへ保存できます。ブラウザ内には入力変更後約0.75秒、クラウドには操作停止後約2秒で保存を予約します。

下書きはアカウントとブラウザの組み合わせ（`userId + deviceId`）ごとに分けます。同じアカウントを複数のブラウザで使っても、編集中の下書きを互いに上書きしません。保存できる有効な下書きは1アカウント10件まで、保持期間は30日です。

他のブラウザの下書きは、更新日時、ブラウザラベル、入力概要を確認してから、選んだものだけを復元できます。復元してもボックスの保存内容は変わりません。下書きの削除も明示操作で行います。計算結果、候補一覧、Workerの状態、チュートリアルは下書きへ含めません。

ページを閉じるときやバックグラウンドへ移るときに、未送信の変更を送信済みとは表示しません。未送信操作は`outbox`へ残し、次回の同期で再送します。リアルタイム共同編集や共有ボックスは提供していません。

### JSONバックアップ

各ボックス画面の`バックアップを書き出す` / `バックアップを読み込む`から、保存済みボックスをJSONファイルとして退避・復元できます。調整対象ボックスと仮想敵ボックスは別ファイルとして扱います。クラウド同期を利用している場合も、JSONバックアップは独立した復旧手段として利用できます。

バックアップファイルを選んだだけでは、作業中の入力条件や下書きは変わりません。バックアップ内の保存を選んで読み込んだ時点で、作業画面へ反映します。

認証済みのアカウントでバックアップを読み込むと、追加・更新・削除・変更なし、競合コピー、重複除外の件数を確認してから、`統合`または`クラウド全体を置き換え`を選べます。読み込めない保存が含まれる場合は、既存データを失う可能性がある置き換えを無効にします。ゲストまたは未ログインの場合は、`統合`または`このブラウザの保存を置き換え`を選べます。

### アカウント・同期管理

ヘッダーのアカウント画面と`Googleでログイン`は、未ログインでも利用できます。Googleログインで受け取るのは、表示名、メールアドレス、プロフィール画像、アカウント識別子です。Google Driveのファイル、連絡先、Gmailのメール本文を見る追加権限は要求しません。

同期状態は、次の7つの文言で表示します。

- `このブラウザのみ`
- `未同期`
- `同期中…`
- `同期済み`
- `オフライン`
- `競合あり`
- `同期エラー`

ブラウザへの保存とFirestoreへの保存は分けて判定します。未送信操作、競合、ネットワーク・権限・利用上限のエラーが残っている間は、`同期済み`と表示しません。必要なときは`今すぐ同期`で再確認できます。

アカウントデータを書き出すときは、手動同期後に、ボックス保存（Firestoreの`syncRecords`）とクラウド下書き（`drafts`）をサーバーから読み直します。読み取りエラー、未送信操作、競合、破損・未対応データが残る場合は、完全な書き出しとは表示せず、警告付きの部分書き出しまたは中止として扱います。

書き出すJSONには、形式の版（`schemaVersion`）、書き出し日時（`exportedAt`）、対象UID、サニタイズしたプロフィール、ボックス、クラウド下書きだけを含めます。認証情報、アクセストークン、Firebaseの公開設定、ゲスト領域は含めません。

アカウント削除では、必要に応じてGoogle popupで再認証します。続いて同じタブの同期と保存予約を停止し、対象UIDの`syncRecords`と`drafts`を最大450件ずつ削除します。両方が空になったことを確認してからUID専用のブラウザ内保存を削除し、最後にFirebase Authenticationのアカウントを削除します。

途中で失敗した場合は、Firebase Authenticationのアカウントを先に削除しません。失敗理由と再試行操作を表示します。最後のAuthentication削除だけが失敗した場合も、ログイン状態を維持して再試行できます。別ブラウザからの同時書き込みを完全には止められないため、削除後にクラウドを再確認してから処理を完了します。

アカウント削除で消すのは、そのUID専用の保存領域です。ログイン前からこのブラウザだけにあるゲストデータ、既存の`championcreator.box.v1` / `championcreator.enemy-box.v1`、既定サンプルの削除状態は残します。必要に応じて、ブラウザのサイトデータ削除や各ボックスの操作で別途削除してください。

<a id="firebase同期の技術境界"></a>

### Firebase・セキュリティ境界

Firebase Web SDK、Google認証、Auth / Firestore Emulator、Firestore Security Rules、App Checkの初期化境界は`src/sync/`へ分離しています。Firebaseの必須Web configがない開発環境ではSDKを初期化せず、ブラウザ内保存だけで動作します。

調整対象・仮想敵ボックスは`/users/{uid}/syncRecords/{documentId}`、ブラウザ別クラウド下書きは`/users/{uid}/drafts/{deviceId}`へ保存します。保存内容のJSON文字列（`payload`）は既存parserで検証し、同期用の版番号、更新ID、server timestampと分離して扱います。

Firestore Security Rulesは未認証・別UIDのread/writeを拒否し、owner UID、kind、許可field、schema、payloadサイズ、revision等を検証します。保存内容のJSON文字列（`payload`）は200,000 UTF-8 bytes以下で、内容のvalidation・migrationはアプリの既存parserが担当します。RulesだけでJSON内部の計算条件を検証する設計ではありません。

FirebaseのWebアプリ用設定（Web config）は公開値として扱います。管理者用認証情報（Firebase Admin credential）、サービスアカウント鍵（service account key）、Google OAuth client secretは、ブラウザ配信用bundleやPages artifactへ含めません。GitHub Pagesの静的構成からFirebase client SDKを利用し、Admin SDKや独自のバックエンドは追加しません。

App CheckはAuth / Firestoreより先に初期化します。本番はCloud FirestoreとAuthenticationへのenforcementを有効にする運用です。Console側の適用状態はコードだけでは保証できないため、公開・設定変更時の確認が必要です。ローカルEmulator、Pages公開設定、Rules、アカウントライフサイクルの手順は[FIREBASE_SETUP.md](docs/FIREBASE_SETUP.md)、保存キー・外部通信・削除対象の詳細は[データ取り扱いの技術詳細](docs/privacy-implementation.md)を参照してください。

## URLで調整を共有する

調整対象の共有ボタンから、現在適用されているH/A/B/C/D/SのSP配分と全シナリオをURLへ埋め込めます。Googleログインや共有用DBは不要です。ボックス全体・アカウント情報・下書き・計算結果・候補一覧は含めず、共有後の手元の編集でリンク内容は変わりません。リンクを持つ人が閲覧でき、配布後の取り消しはできません。

- 新しく発行するURLは`/?import-share=1#share=s1.…`です。メインページの通常の起動・保存先確認後、直接「共有された調整を取り込む」を表示します。取り込み前にポケモン画像、シナリオ数、H/A/B/C/D/SのSPと実数値を確認できます。実数値は共有された配分を既存のCalc変換経路で評価し、表示できない場合は明示します。Googleログインは任意です。同期を利用中の場合は、通常どおり初回同期の確認を経由します。
- 「作業に読み込む」か「ボックスに追加」を選ぶまで自動保存を止め、キャンセル時は元の作業を維持します。作業への読み込みは現在のブラウザ内保存の成功後に反映し、進行中の探索と旧結果を破棄します。ボックスへの追加は新規IDで保存し、既存の下書き・ボックスを置き換えません。成功通知は4秒で消えるトーストとして表示し、画面の操作や入力状態を変えません。ログイン中は既存のアカウント保存・同期経路を使用します。

### s1形式と復元互換性

条件schema 13の初期値をURL形式s1に固定し、gzip／Base64urlで圧縮します。画面用IDは再生成し、型・数値範囲・版・展開サイズを検証してから既存parserへ渡します。今後初期値を変更する場合もs1の省略値は変更しません。

省略値の正は[`urlShareDefaultsV1.ts`](src/share/urlShareDefaultsV1.ts)の`SHARE_TARGET_V1` / `SHARE_ATTACK_V1` / `SHARE_SCENARIO_V1`です。現在の画面の`createDefault*`へ追従させません。例えばs1の`speedRequiredOffset`の省略値は1で、以後の画面既定値と独立します。固定s1 URLは[testFixtures](src/share/testFixtures/)で復元互換性を保持します。

復号上限はtoken 16,384文字、展開JSON 200,000 bytes、64シナリオ、全攻撃256件です。型・数値範囲・版・圧縮データの破損・上限超過を確認し、無効な共有を入力の自動補正に依存して取り込みません。これは次節の「新しく発行するURL全体」の上限とは別です。実装は[urlShareCodec.ts](src/share/urlShareCodec.ts)と[sharedAdjustment.ts](src/share/sharedAdjustment.ts)です。

### URL長・公開範囲・アクセス解析

アプリが新しく発行するURL全体は4,000文字以内です。2,000文字を超えるとDiscordの通常メッセージの文字数制限を案内します。シナリオ数だけで長さは決まらず、攻撃数やラベル等でも変わります。

共有URL試験では、Xで約4,000文字のケースはURLとして認識され、約8,000文字は認識されませんでした。これは個別条件での観測です。Discord無料アカウントの通常メッセージを想定した2,000文字の注意表示も、URL自体が本文の文字数に含まれる前提のアプリ側の案内です。いずれもXやDiscord全体の公式上限・すべての転送経路での動作保証ではありません。

取り込み先は通常の本体ページで、本体のアクセス解析が動作します。解析の`page_location`にはoriginとpathnameだけを設定し、query／fragmentの共有内容を含めません。共有URLごとのページをsitemapへ生成せず、SNSプレビューはCC共通画像を使います。調整ごとのOGP画像生成は行いません。本体経路に専用のnoindex設定や解析停止はありません。根拠は[index.html](index.html)と[共有取り込みのテスト](src/share/ShareImportDialog.test.tsx)です。

## ビルド・静的配信

`npm run build`は通常のVite build後に`scripts/prerender.mjs`を実行し、実際のAppから白紙の初期画面をHTMLへ生成します。ブラウザの保存内容や認証情報は生成に使いません。JavaScriptの起動後は`createRoot`でこのブラウザの状態を復元するため、ビルド時の白紙状態を保存済みの入力へhydrateしません。起動前に入力した値が置き換えで失われないよう、静的プレビューのフォーム操作は無効にし、ガイドへの通常リンクは維持します。計算や編集には引き続きJavaScriptが必要です。

公開ガイドの「計算例と結果の読み方」は、チュートリアルと同じ入力JSONを既存parserで読み、同じCalc・耐久探索・火力/素早さ条件の統合経路でビルド時に計算します。結果を手作業で固定せず、条件を満たす候補がちょうど1件にならない場合はbuildを停止します。JavaScriptを実行しなくても、この計算例とガイド本文を読めます。ルートの`favicon.ico`も既存の32px PNGから生成します。

チュートリアル・計算例・ボックスの入力は[既定サンプル](#既定サンプルと白紙初期状態)にまとめています。PWAはWeb App Manifestに対応し、Service Workerによるオフラインキャッシュは未実装です。ブラウザ内保存が利用できることと、サイト全体をオフライン起動できることは別です。

Pages公開では`npm run retain:deploy-assets`が、公開中の`assets/asset-history.json`を読み、直近30日間に現行buildで使われたhash付きJS・CSSを元の名前・内容のまま保持します。初回だけ公開中のトップ・guide・privacyと、それらのJSが参照するWorker・動的importなどから保持対象を検出します。通常のbuildはローカルで完結し、この保持処理だけが公開サイトへアクセスします。

保持ファイルはSHA-256・サイズ・パス・日時を検証し、取得失敗、同名別内容、破損manifest、保持分512 MiB超過では公開を停止して既存の配信を守ります。古いファイルの保持期限は、単に引き継いだだけでは延長しません。この処理はViteが出力先を空にした直後のbuildへ1回実行します。すでに公開から消えていたファイルを、新しい内容で同名復元することはしません。

検索向けの確認対象はHTML本文、canonical、robots、サイトマップ、Googleでの実際の取得・描画です。取得・描画が成功してもGoogleのインデックス登録や検索表示を保証しません。静的HTMLの生成は[prerender.mjs](scripts/prerender.mjs)、保持処理は[retain-deploy-assets.mjs](scripts/retain-deploy-assets.mjs)、公開手順は[Pages workflow](.github/workflows/deploy-pages.yml)を参照してください。

## 制限

- 本ツールは非公式のファンツールです。ゲーム内の結果と完全に一致することは保証しません
- 使用率順は Pokemon Champions Battle Data の `Current` データに基づくため、提供元の更新状況によって反映まで時間差が生じる場合があります
- Pokemon Champions と Showdown の仕様差、未対応データ、特殊処理により、実際のゲーム内結果と異なる可能性があります
- 一部のフォーム違い、技、特性、持ち物は未対応または仮対応の場合があります

- 直接攻撃の計算対応は[固定Calc・patchの範囲](#直接ダメージ計算の責任範囲)、明示HPイベントと完全な対戦進行の違いは[HPイベントの評価](#hpイベントの評価)を参照してください。
- [通常タイプ指定](#通常タイプとテラスタル)は変化後の状態入力であり、技の成功・発動順を自動判定しません。[威力指定](#威力指定と現在hp依存技)と[素早さの手動倍率](#素早さラインの条件)にも適用範囲があります。
- [キョダイマックス](#ダイマックスキョダイマックス)は未対応です。metadataの先行対応とmechanicsの計算対応は[対応状態](#metadataと計算対応)で区別します。
- [残りSPで耐久最大化](#残りspで耐久最大化)は耐久指数の比較で、通常探索のシナリオ合格を保証しません。
- リアルタイム共同編集、共有ボックス、Google以外のログイン方法、チュートリアルの永続化は対象外です。クラウド下書きの利用条件・10件上限・30日保持は[保存仕様](#ブラウザ別クラウド下書き)を参照してください。

- 条件が複雑なほど探索に時間がかかります
- 重要な調整は実機でも確認してください

### URL共有の検証

共有URLの往復、文字数・展開サイズ上限、破損データ、SPと実数値の表示は`npm test -- src/share`で確認できます。固定のサンプルと省略値を固定した既発行s1形式のURLは`src/share/testFixtures/`に保ち、現在の初期値とは独立して復元互換性を検証します。

SNS経由の確認には、本体の共有ボタンで作成したURLを使います。公開ドメインで作成したリンクをSNSへ投稿・送信し、届いたリンクから取り込み画面が開くこと、配分とシナリオが一致することを確認してください。SNSアプリ内ブラウザと外部ブラウザの双方で確認します。自動テストはSNS側の文字数制限や転送経路の確認を代替しません。
